# Skillful Grill — Plan Validation

## Overview

Stress-test the approved design before it becomes a detailed implementation plan. The goal is to find holes, broken assumptions, and feasibility issues while changes are still cheap.

**Core principle:** A flaw caught here costs minutes. A flaw caught during implementation costs hours. A flaw caught after shipping costs days.

The grill interviews the USER directly — one question at a time with your reasoning. Nothing changes without the user's answers.

## When to Use

After the spec is generated by brainstorming, before writing-plans is invoked.

## The Process

### Step 1: Review the Spec and Loaded Skills

Read the spec from `.skillful/spec.md`. Check what skills are installed. Identify areas where the spec might conflict with reality.

### Step 2: Check for Common Issues

Systematically check the spec against these categories. For each category, ask the user ONE question at a time if you find a potential issue:

**Feasibility:**
- Is the tech stack choice workable for the stated requirements?
- Are there known limitations or breaking changes in the chosen versions?
- Do any loaded skills suggest better approaches that conflict with the spec?

**Completeness:**
- Are there obvious missing pieces? (auth, error handling, data persistence, deployment)
- Are edge cases acknowledged or silently assumed away?
- Are success criteria measurable?

**Consistency:**
- Do different sections of the spec contradict each other?
- Do the proposed dependencies actually work together?
- Are there version conflicts the spec doesn't mention?

**Scope:**
- Did the spec grow beyond what was agreed during triage?
- Are there nice-to-haves masquerading as requirements?
- Is any piece too vague to implement from?

**Risk:**
- What's the riskiest part of this design?
- What would fail first if something went wrong?
- Is there a simpler path with less risk?

### Step 3: Ask Questions (One at a Time)

For each issue you find:
1. State the issue and your reasoning
2. Suggest an answer or resolution
3. Ask the user: "Does this concern you? Should we adjust?"

**One question per message.** Wait for the user's response before asking the next one.

### Step 4: Solidify the Plan

After all issues are addressed:
- Update `.skillful/spec.md` with any changes
- Save `.skillful/handoff.md` with state `spec` (create if missing) — include summary, tech stack, architecture, spec path, key decisions
- Confirm with the user that the validated spec is ready
- Hand off to writing-plans for detailed implementation tasks

### Step 5: Handoff

Announce: "Spec validated. I'll now create the detailed implementation plan."

**REQUIRED SUB-SKILL:** Use skillful:writing-plans to create the implementation plan.

<HARD-GATE>
Do NOT hand off to writing-plans until the user has confirmed the spec is ready. An unvalidated spec produces an unreliable plan.
</HARD-GATE>

## Red Flags

- Skipping the grill because "the spec looks solid" — every spec has holes
- Asking multiple questions at once — one at a time
- Suggesting implementation details instead of validating the design
- Accepting "we'll figure that out later" for a blocking issue
- Not checking loaded skills for conflicting guidance

## Key Principles

- **Interview, don't rewrite** — Ask the user, don't silently change things
- **One at a time** — One question per message
- **Suggested answers** — Give the user something to react to
- **Cheap fixes now** — A question now saves hours of rework later
- **Skills are your reference** — Use loaded skills to inform your questions
